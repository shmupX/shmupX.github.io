## Content that cannot ship in a Steam depot

- **The four arcade eShop rows** are commercial MAME romsets from Banpresto, SNK and Sega, streamed from the deploy on first play. Steam will not accept third-party ROMs, so the Steam build needs a catalog without those rows, and the arcade keep-and-serve path in `lib/streamed-payloads.ts` goes with them.
- **The staged Dezaemon cartridges.** Running `deno task build` on a machine that holds the dumps stages Athena's SFC cart and the Dezaemon 3D cart plus Nintendo's IPL into the static tree, and the packager embeds the whole built client tree. A Steam build cut on a maintainer's machine would carry those ROMs. Either exclude those two folders in the packager or only ever cut Steam builds on a clean runner, as the release workflow already does.
- **Post-install downloads.** Steam expects the game's content in depots, not fetched from your own servers after install. The custom BGM for the shipped game is small enough to stop excluding and embed instead. Super Mario SP is already left out, so nothing changes there.
- **Online services.** The level catalog is an open-write Firebase database and netplay runs on SpacetimeDB. Neither is a build change, but the store questionnaire asks about them, and the launcher has to keep working when they are unreachable.

## Changes to the three launcher builds

- **Windows: stop using `deno compile` for the Steam build.** The single-file requirement came from the non-Steam shortcut flow. A depot is a directory, so the `deno desktop` layout of a launcher exe beside its runtime DLL is exactly right. The compile route has no engine and borrows Chrome or Edge. That leaves nothing in-process for the Steam overlay or Steam Input to hook, makes Steam's process tracking depend on a browser child, fails under Proton where no Edge exists in the prefix, and carries no desktop version. It also shows a console unless the no-terminal flag is passed, which is currently opt-in.
- **Linux: ship the plain app directory, not the AppImage.** Pass the existing no-appimage flag and make `AppRun` the launch executable. Steam runs Linux titles inside the Steam Linux Runtime container, which has no FUSE for the AppImage mount. The whole install-to-data-dir machinery exists to work around the AppImage's read-only mount and is moot in a Steam library folder. Upload from a Linux runner so the executable bits survive. CEF's sandbox inside the runtime container is untested here and needs a real run.
- **macOS: arch and signing.** The cross-build default is arm64 only. Build x86_64 for the depot, which Rosetta runs everywhere, or lipo both into a universal on a Mac. The in-process ad-hoc codesign is enough for Steam to launch it, since Steam downloads carry no quarantine flag.
- **Turn the self-updater off at build time.** Steam delivers updates through depots. On a plain Linux directory the launcher reports itself as an ordinary executable, so the updater arms and would patch its runtime library inside the Steam library folder, where "verify integrity" reverts it and the files diverge from the depot manifest. The only off switch today is an environment variable, which Steam launch options cannot set, and the signing key was deliberately kept out of the environment for the same reason. The fix is a build-time marker, for example a `--steam` flag in the packager that embeds a small JSON file the update plan reads.
- **Hide the Steam-shortcut surfaces under that same marker.** ADD TO STEAM, the first-run nudge in `static/steam-nudge.js`, and the install step have no meaning once the app is already in Steam. Do not key this off Steam's environment variables, because the launcher already runs under Steam as a non-Steam shortcut where those are present.
- **Overlay and input.** The browser environment scrub that removes Steam's preload library only matters on the compile route. With CEF everywhere, the overlay still has to be tested, since Chromium GPU processes and the overlay have a history. Steam Input presents a virtual Xbox 360 pad, which the existing Xbox rule in the gamepad support script already matches.
- **Saves and Steam Cloud.** Under `deno desktop` the page's storage does not survive a launch. Only two kept keys persist, in a JSON file under the launcher's data directory. Decide what counts as a save before pointing Auto-Cloud at that directory.

## Packaging and pipeline

- Add a Steam output mode to `packages/shmup-harbor/scripts/build-desktop.ts` that writes the three plain layouts into one tree, with the marker and the content exclusions above applied.
- Extend the release workflow, which today builds only the Linux AppImage, to build all three targets on the Linux runner and upload with steamcmd using app and depot build scripts. Cross-building Windows and macOS from Linux already works.
- Skip Steam's DRM wrapper. A Deno executable carries its payload appended to the binary, and the wrapper is built for ordinary native executables.
- Keep the version in `deno.json`. Depots carry their own build IDs, and the baked desktop version still feeds the UPDATES row even when updating is off.
