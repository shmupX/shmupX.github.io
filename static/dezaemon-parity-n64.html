Dezaemon N64 Parity Mapデザエモン3D

The odd one out among these four maps. The other three describe parsers that exist — the Saturn map, the Super Famicom one, the PlayStation one. This one describes a format, not a parser. Nothing in this repo reads dev-fixtures/dezaemon298.ddd: there is no packages/shmup-engine/src/n64, no n64:probe, no test, not one line. What exists instead is a read path proven end to end outside the repo — all 60 files extract, and 58 of them decompress to exactly the byte size third-party documentation predicts, using this repo's own LZSS decoder unmodified. Target is the unreleased 64DD expansion for Dezaemon 3D (Athena, 1997): a prototype data disk written 1998-02-23 19:24:25 from a Partner-N64 unit, disk ID DEZA, carrying a filesystem that is Athena's own (ATNFS0) and not Nintendo's MFS. Surveyed 2026-09-19. No canonical notes file yet — packages/shmup-engine/FORMAT-N64.md does not exist.

.ddd = .ndd minus the 24-LBA system area → libleo LBA → byte 85 sectors × 232…112 → ATNFS structure-of-arrays · names · startLBA · blockCount · u32 stored size → Okumura LZSS (decompress.js, unmodified) → per project GAM · CGR · CMD · CBL · ULB · MUS + 8 stages × {BL · MD · GR} ‖ no parser · no probe · no FORMAT-N64.md · no game.json · no write path · no launcher row
Format knowledge Confirmed the container, the read-only directory, the codec, and the two graphics types — 8,683,520 of the 12,596,477 bytes a project decompresses to, 69%, and it is that high for the same reason as on the PlayStation page: the graphics are two thirds of the payload Likely CMD · CBL · ULB · #BL · #MD · GAM and the writable directory — 3,638,925 bytes, 29%: documented field by field by a third party whose arithmetic closes exactly, and not yet checked struct by struct against these bytes Open the MUS sequence body — 274,032 bytes, 2%: 24 songs of 0x2C9A of which only the 0x1A-byte header is described
Shipped in this repo Nothing. Zero bytes of the above are read by any code under packages/, tools/ or static/. Every measurement on this page was made in a scratchpad and none of it is committed. This bar is the honest difference between this map and its three siblings, and it is the whole of section 04.

01What remains

Unusually for these maps, almost none of what remains is reverse engineering. The format was closed in a single pass (2026-09-19) once the prior art was found — a canonical dump of the same disk on 64dd.org and a field-by-field format document shipped with a 2024 fan translation. What remains is mostly writing the code. MEANING OPEN means bytes located at a stride something gives but whose semantics are untraced; NO TRACE means nothing exists yet.

  1. 1

    The parser itselfNO TRACE

    This is item one because it is the only thing standing between this page and its siblings. The read path is proven — see section 02 — but it lives in a throwaway script. Nothing is committed: no packages/shmup-engine/src/n64/, no "./n64" subpath export, no tools/n64-ddd/main.ts, no n64:probe task, no tests/dezaemon_n64_test.ts. The 58-of-60 size match is the acceptance test to build against, and the scaffold is three times precedented in tools/psx-sav, tools/sfc-sav and tools/deza-disc. Estimated at a day for container plus filesystem on top of half a day of scaffolding — which is small enough that the absence is a scheduling fact, not a technical one.

  2. 2

    The zone table above LBA 368MEANING OPEN

    All 60 sample files live below user LBA 368, where the LBA-to-byte map degenerates to two zones — lba × 19720 under LBA 268, then 268 × 19720 + (lba − 268) × 18360 — and that is what the extraction actually used. The writable area starts around LBA 1417, and reaching it needs the real thing: two heads, sixteen physical zones, and a per-disk-type vzone → pzone permutation. The multiset of sector sizes is certain and the tables are published for disk type 0, but the ordering is not a monotone 232→112 descent and hand-rolling it will be quietly wrong. Copy leo64dd_python or leotools's leogeo.c, and assert the cumulative total equals 64,458,560.

  3. 3

    How big the directories actually areMEANING OPEN

    The read-only directory has 60 populated entries and the writable one 21 used slots — 11 live including DEZA3D.SYS, DEZA3D.HSC and nine files of a user project DST, plus 10 tombstoned. Those counts are measured. The capacities — 834 and 480 slots, the latter reading as 16 projects × 30 files — are inferred from the strides between the parallel arrays, and those strides run through zero fill, which cannot distinguish a large array from a small one followed by padding. One disk cannot settle it. Take the slot count as a parameter; do not hard-code 480.

  4. 4

    The MUS sequence bodyMEANING OPEN

    24 songs of 0x2C9A each, 0x42E70 total, and the documentation describes the 0x1A-byte header and stops. That leaves roughly 11.4 KB per song of sequence data with no reading at all — the single largest undocumented run on the disk and the whole of the open band in the meter above. It is also the one item with no cheap route: the playback code is on a cartridge nobody has, so it would have to come out of the bytes alone. Budget a week and expect it to resist.

  5. 5

    The fields the documentation marks ???MEANING OPEN

    Its author says so plainly — "please note these are not complete!" — and leaves named gaps: #MD +0xC11..0xC1F, #BL 0x47, 0x5B and 0x8B2F, and GAM 0x1, 0x225, 0x557, 0x558. Separately, one of its counts is demonstrably wrong: it claims 520 images for #GR, and 0x104000 ÷ 2 bytes ÷ (64 × 32) is 260. Take its dimensions, not its totals, and re-derive every count from the size.

  6. 6

    Why the two GAM files are nine bytes shortMEANING OPEN

    SAMPLEZ1.GAM and SAMP.GAM decompress to 1,360 bytes where the documented structure is 1,369 — the only two misses in sixty, and the deficit is identical. This is not a defect in the read path: the same documentation warns by name that "in the recovered prototype disks, SAMPLEZ1 & SAMP's GAM file data has slightly different, incompatible formatting", and these are exactly and only those two files. So the miss is a fourth independent confirmation that the chain is right. What the nine bytes are is still unknown, and a retail disk would presumably settle it — except no retail disk exists.

  7. 7

    The DezaDiskTool bytecodeNO TRACE

    The fan-translation release ships DezaDiskTool.exe, a PyInstaller bundle whose three Python bytecode bodies were extracted during this survey but not decompiled: the tool proper (46,491 B — a Filetable class, a known_sizes table, an 8.3 name helper, an LBA-usage checksum), its LZSS module (10,359 B), and an N64 helper (40,813 B). Running pycdc or decompyle3 over them would hand over the size table and the exact list of which extensions are compressed as someone else's tested code rather than as inference. Half a day, and it retires most of items 3 and 5. This is the highest-value unspent hour on the page.

  8. 8

    This fixture is the wrong dump for the save areaMEANING OPEN

    64dd.org labels our file the "Old Dump" and hosts DEZA_1_19980223.zip as current. They differ in 175,897 bytes, every one of them inside the save area (0x18CF180–0x1922C3F); the ROM area holding all 60 sample files is byte-identical, so nothing else on this page is affected. But the DST user project lives in exactly the region that differs, and a 2021 64dd.org note describes correcting a dump that "may have been tampered by accident". If anyone parses DST, use deza1.NDD, not this fixture.

  9. 9

    No controlled delta is possible hereNO TRACE

    The method that promotes a claim to confirmed on the other three maps — change one thing in the editor under an emulator, save, diff — cannot be run. It needs a 64DD emulator, a disk writer, and the DEZA64 cartridge, and the cartridge was never released. So for this platform confidence tops out at likely for anything not provable by arithmetic. That is precisely why the exact-size test in section 02 carries so much weight: it is the only arithmetic proof available, and it happens to cover the entire chain at once.

  10. 10

    A viewer, and then the ceilingNO TRACE

    Worth stating plainly so nobody plans past it. Neither psx-sav nor sfc-sav output ever reaches this repo's game.json; the only pipeline into a playable level is the Saturn .sav path. And Dezaemon 3D is a 3D shooter whose data model — s16 vertex meshes, baked per-face lighting, texture tile descriptors — does not obviously map onto a chip-grid 2D level. So the credible deliverable is a viewer, in the shape sfc:probe and psx:probe already have: report, hex, png, then FORMAT-N64.md, then a shelf cover. A launcher row is not reachable at all — static/emulators.json has no N64 core, and the disk needs a cartridge that does not exist.

02Already decoded

Confirmed Measured against the bytes of dev-fixtures/dezaemon298.ddd and reproduced independently. As everywhere on these pages, "confirmed" never means a runtime consumes the result — here nothing does, and nothing in this section is committed to the repo.

FeatureWhat is decoded, and what pins it
The whole read pathThe load-bearing result. Using only the directory arrays, a two-zone LBA→byte function and this repo's existing packages/shmup-engine/src/decompress.js, all 60 files extract and 58 decompress to exactly their documented size — CGR 163,840, ULB 57,600, CMD 62,120, MUS 274,032, 0GR 1,064,960. The two misses are the two GAM files, both short by the same 9 bytes, and the documentation names those two files as malformed on the prototype disks (item 6). Landing five distinct types on exact sizes up to a megabyte is not reachable by chance, and this one test confirms the LBA mapping, the directory layout, the codec and the third-party documentation simultaneously.
What the file isThe user data area of a 64DD disk — not a ROM, and there is no N64 ROM magic anywhere in the 64 MB, nor should there be (the 64DD IPL jumps straight to LBA 24 with no header). Settled by byte comparison against 64dd.org's canonical deza1.NDD: the sizes differ by 473,280 = 24 × 85 × 232, exactly the system area, and deza1.NDD[473280:] is byte-identical to this file except in the save area. So .ddd is .ndd with the 24-LBA system area sliced off — an ad-hoc 2018 dumper's extension, not a format any spec, tool or emulator names.
The disk's own wordsAt 0x28E80, in romaji: KONO DISK WA DEZA64 DATA DISK DESU / ICHIDO DENGEN WO KIRI DEZA64 NO / ROMCARTRIDGE WO SOUNYUUSHITE / DENGEN WO IRENAOSHITE KUDASAI — "this is a DEZA64 data disk; power off, insert the DEZA64 ROM cartridge, power on again". DEZA64 is Dezaemon 3D's internal codename, and the sentence is the disk stating its own dependency on the cartridge that was never released.
The system areaAbsent from our file, recovered from the canonical dump: region E8 48 D3 16 (JP), format type 0x10, disk type 0, Disk ID DEZA with BCD timestamp 1998-02-23 19:24:25, PTN64 (written from a Partner-N64 development unit) and ATNFS0 in the free area. One trap worth recording: the ROM-end / RAM-start / RAM-end LBA fields at 0xE0 read 1016 / 1C22 / 282E, which is an arithmetic sequence stepping by 6 and past the maximum LBA — filler, not data. The disk does not record where its own ROM area ends.
The ROM/RAM splitRecovered from the data instead, and unambiguous: exactly one large 0xFF run, 0x6C7188–0x18CA9C8, 18,888,768 bytes of unwritten media. The last sample file's stored extent ends at 0x6C7187, flush against it. That run is blank media, not corruption, and region 2's 6.2–7.7 bits/byte is LZSS output, not encryption.
Container geometryA linear concatenation of variable-size blocks in libleo LBA order from user LBA 0 (physical LBA 24). A block is 85 sectors; sector size is one of 232/216/208/192/176/160/144/128/112 by zone; 4,292 blocks summing to exactly 64,458,560. Nothing here needs reverse engineering — the tables are published on LuigiBlood's 64dd wiki and implemented in leo64dd_python, leotools, Project64 and mupen64plus-core. The first hint came from the file itself: the gaps between the directory's backup copies are exact sums of block sizes, 34,680 = 85×192 + 85×216 and 48,960 = 3 × 85×192.
The directory (read-only)Athena's own ATNFS, and a structure of arrays, not packed records — which is why earlier passes found names and no sizes. Base 0x18CA9C8, 60 entries: names char[11] = NAME(8, space-padded) + EXT(3) with no separator at 0x18CAD0A; u16 big-endian start LBA at 0x18CD0E0; u16 block count at 0x18CD764; an all-zero u16 array at 0x18CDDE8; and u32 big-endian stored size at 0x18CE46C — that last array is the one that makes extraction possible. Allocation is contiguous: startLBA[i] + blockCount[i] == startLBA[i+1] for all 59 pairs, LBA 9 → 368. Replicated byte-identically at 0x18D3482 and 0x18DF3C2, all three at in-block offset 834 — redundant backups.
CompressionOkumura LZSS, and packages/shmup-engine/src/decompress.js decompresses these files unmodified — the same parameters as the PlayStation Dezaemon 2 work already shipped here: 4096-byte ring zero-filled, write pointer at 0xFEE, flag byte LSB-first, 1 = literal, 0 = 2-byte match with off = b1 | ((b2 & 0xF0) << 4) and len = (b2 & 0x0F) + 3. Corroborated independently: the LZSS module inside DezaDiskTool.exe self-describes as a port of Okumura's codec. The trap: this decoder cannot fail — it will happily "decompress" noise, and one pass of this very survey was misled that way. It is evidence only when the caller supplies the stored length from the directory and the output length matches a predicted value. There is no length prefix on these streams.
Graphics formatN64 RGBA5551, 2 bytes per pixel, no palette, on flat 64-pixel-wide scanline sheets — not the rgb555ToRgb unpack the PSX and SFC parsers use, since the alpha bit is bit 0. Pinned by measurement: of the 432,506 nonzero big-endian 16-bit words in SAMPLEZ1.0GR, every one has bit 0 set, fraction 1.000000, and the same holds for all 29,180 in CGR. Nothing but an alpha bit produces that. It also corrects the documentation's image count — 0x104000 ÷ 2 ÷ (64 × 32) is 260, not 520. Rendered as a contact sheet the tiles are unmistakably real art: the sample game's GEAR SQUID title logos, WARNING and DANGER plates, a CODE NAME DUAL-LANCER briefing screen, sys check 01/02, and Japanese cut-in portraits.
The model record0xC20 bytes, and the pleasant surprise of the survey: plain data, not F3DEX display lists. +0x0 u8 vertex count (≤100), +0x1 u8 face count (≤100), +0x2 100 vertices of s16 x,y,z, +0x25A 100 faces of 0x14 bytes (three vertex indices, three s16 UV pairs, three bytes of baked RGB light, one flags byte), +0xA2C 16 tile descriptors, +0xBAC per-vertex groups. Corroborated by a scan of the whole 64 MB, which found only 4 G_ENDDL and 1 G_RDPPIPESYNC, all inside the boot stub. The engine builds display lists at run time; the disk stores geometry as structs, so a viewer is direct.
The project model30 files per project: 6 globals — GAM CGR CMD CBL ULB MUS — and 3 per stage, BL MD GR, for stages 0,1,2,3,4,5,6,8. Stage 7 is simply absent from the numbering. The disk carries two pressed sample projects, SAMPLEZ1 and SAMP, plus the global DEZA3D.SYS and DEZA3D.HSC and a user project DST in the writable area.
The boot program DEAD ENDRecorded here so nobody spends a day on it. File 0x0–0x29420 (168,992 bytes) is a complete libultra executable, load address 0x80000400, entry 0x80000560; the entry stub's bzero loop gives the BSS bounds (t0 = 0x80029820, length 0x48180 — note the addiu sign-extends, so it is not 0x8003xxxx) and 0xFF filler begins on exactly the byte BSS starts, which pins both the load address and the image end. It holds ~3.9 KB of genuine 64DD block-mode driver (ASIC registers 0x05000508/0x05000510, sector buffer 0x05000000) and no filesystem code at all — not one filename constant, no DEZA3D, no extension table. All 274 jr ra instructions in the 64 MB fall inside this image; there is no code anywhere else on the disk. Its entire job is the "insert the cartridge" screen. Do not disassemble it hoping to find the filesystem — that lives on the cartridge, and it is no longer needed.

03Located but not yet understood

Likely Every one of these has a documented layout whose arithmetic closes exactly against the measured file sizes — CBL = 27 × 0x5C, CMD = 20 × 0xC20 + 40, #MD = 130 × 0xC20 + 260, ULB = 8 × 0xC20 + 8 × 0x1000, CGR = 40 × 0x1000. That is a strong prior and it is not the same thing as having been checked field by field against these bytes, which none of them has. The source says of itself "please note these are not complete!", and one of its counts is already known wrong (item 5), so everything here should ship marked likely.

  • CMD 0xF2A8 — 20 model entries of 0xC20 plus 20 texture indices; the record itself is confirmed (section 02), the surrounding table is not
  • #MD 0x62944 — 130 model entries of 0xC20 plus 260 bytes, per stage: by volume the largest likely region on the disk, and the one a viewer would reach first
  • CBL 0x9B4 — 20 enemy entries and 7 item entries of 0x5C each
  • ULB 0xE100 — 8 models and 8 textures, the only file mixing the two record kinds in one container
  • #BL 0x8B37 — 180 enemy entries of 0x5C, enemy placement, a 256-entry map table and 500 layout-effect commands of 0xC; three named ??? fields inside it
  • GAM 0x559 — global settings, two 0xA0 high-score blocks, ~120 s16 sprite-atlas coordinates, 30 light entries and a 0x200 editor palette — and nine bytes that do not reconcile on this prototype (item 6)
  • MUS header — the 0x1A bytes at the head of each of the 24 songs are described; the 0x2C80 after them are not (item 4)
  • The writable directory — same structure-of-arrays shape at ~0x18CF174, one 16,320-byte block, with a per-block u16 allocation map at 0x18CF182 where 0xFFFF means free and anything else is the owning slot index. Two traps a naive reader will hit: save-area files can be fragmented — DST.MUS claims start LBA 1428 count 3 but the map places it on 1428, 1429 and 1451, so startLBA + count is valid only in the read-only area — and there is no checksum anywhere in either directory, so unknown fields must be preserved verbatim rather than recomputed. Deletion is FAT-style: zero the first byte of the name.

04No trace at all

Absent Unlike the other three maps, this section is not a short tail — it is nearly everything this repo would have to contain. None of section 02 is committed.

  • Any parser — no packages/shmup-engine/src/n64/, no "./n64" subpath, no reader of any kind (item 1)
  • Any tool — no tools/n64-ddd/, no n64:probe task in deno.json, no report/hex/png verbs, no README row
  • Any test — no tests/dezaemon_n64_test.ts. The fixture is correctly placed already: dev-fixtures/ is gitignored, so a test would be ignore:-gated on its absence and must exit 0, not 1, when it is missing
  • Canonical notes — no packages/shmup-engine/FORMAT-N64.md, which is where the confirmed/likely/open split on this page properly belongs
  • A cover — no counterpart to packages/shmup-engine/src/sfc/cover.js, and the graphics to build one from decode today
  • The game.json mapping — and unlike the other platforms this may never be the right goal: the data model is 3D (item 10)
  • Any write path — nothing writes .ddd or .ndd. It would be unusually tractable if wanted, since there are no checksums to satisfy — but the fragmentation rule and the allocation map must both be honoured
  • A launcher row — static/emulators.json has no N64 core, and the disk is inert without a cartridge that was never released
  • A round trip — impossible here rather than merely undone, for want of an emulator, a disk writer and the cartridge (item 9)
